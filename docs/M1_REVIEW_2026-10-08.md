## Correctness blockers

1. **Historical metrics get the current version label.** `app/telemetry.py:156` queries version without evaluating at the requested historical time. A v1 healthy window requested after v2 deployment can be saved as a v2 baseline. Rollback validation compares after.version to baseline.version, so this can reject a valid v1 rollback. Historical windows spanning versions also need explicit handling.

2. **Recovery does not enforce post-action evidence.** `app/service.py:193` checks a single snapshot. It does not reject future action_completed_at or require telemetry to be measured after the action. Reproduced with test providers: completion one hour in the future still returned recovered=true and recovery_time_seconds=0. Prometheus rate windows can also overlap the pre-action period. Require valid timing and sufficient post-action measurements.

3. **Unknown scenarios bypass action-specific checks.** `app/service.py:202` defaults scenario_checks_passed to true and chooses checks using substring matching. Reproduced a captured bad_deployment incident with v1 baseline, current healthy v2, and validation scenario bad_release: recovered=true despite no return to v1. Validate scenario values and require consistency with captured evidence.

4. **Freshness is checked against query-result timestamps.** `app/telemetry.py:71` uses timestamps from aggregate expressions, which can represent evaluation time rather than source scrape time. Verify source sample age and scrape availability to enforce stale_after_seconds reliably. Default rate windows may still fail on missing data; the concern is the explicit stale guard.

5. **Baseline creation lacks quality gates.** `app/baseline.py:36` requires only a nonempty window. It can save sparse or unhealthy data as healthy and inflate recovery thresholds. Require minimum coverage/samples, stable version, real traffic, and acceptable health/error criteria or an explicit verified healthy collection workflow.

6. **Kubernetes setup is incomplete.** README applies Prometheus to nexus-demo before creating the namespace. M1's Kubernetes manifest expects Loki, but Kubernetes Loki/Alloy manifests are absent. The current Docker stack cannot provide Kubernetes/deployment evidence.

Secondary issues: storage filename sanitization can collide for distinct IDs; deployment SUCCESS checks should include updated replicas and observed generation; GET window validation inside the handler can return 500 for invalid start/end ordering.

## Verdict

The Docker observability path is demonstrably working under traffic. M1 is not yet fully ready for reliable recovery sign-off or the complete Kubernetes demo. Fix the correctness blockers and prove real bad-deployment rollback and traffic-spike scaling with stored before/after evidence. This review did not inject faults, change replicas, or execute remediation.
